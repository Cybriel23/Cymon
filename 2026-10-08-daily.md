## 1. Risk Watch

### 1.1 Atlassian CVE-2026-21589: exploited within two hours of public detail, and the Crowd chain turns a file read into Jira admin (follow-up, ESCALATION, EXPLOITED)

Yesterday this was a breadth problem with no exploitation. Today it is both. **watchTowr published its technical analysis on 6 October; Previdian reported exploitation attempts hitting its honeypot network within about two hours**, and a **public PoC is now on GitHub (`tc4dy/CVE-2026-21589-PoC-Exploit`)**, with SANS ISC separately reporting scanning. The root cause is in **`atlassian-plugins-webresource`** (vulnerable 6.0.7, fixed 6.0.8), in `Router.java`: helper methods convert forward slashes to **`::`** and back, and because the path filter looks for slashes, a traversal written as **`..::..::`** survives the check and is converted back to `../` afterwards. The traversal needs a plugin resource whose `location` ends in a trailing slash — watchTowr used Jira's **`color-picker`** image directory. Example request: **`/download/resources/jira.webresources:color-picker-popup/images/..::..::..::..::..::WEB-INF::web.xml`**; equivalent routes exist for Confluence (`com.atlassian.confluence.plugins.dashboard-actions`) and Bitbucket (which blocks `web.xml`, so **`urlrewrite.xml`** is read instead). Reads are confined to the Tomcat application context. **The detail that changes the risk calculus:** where Jira is integrated with Atlassian Crowd, **`WEB-INF/classes/crowd.properties`** yields the application name, the **application password in plaintext**, and the Crowd server and base URLs — with which watchTowr listed users through Crowd's REST API, created a user, and **added it to `jira-administrators`**. Crowd IP allowlisting breaks that chain; absent it, "unauthenticated file read" is unauthenticated Jira administrator. **Affected: all versions** of Bitbucket, Confluence, Jira Software, Jira Service Management, Bamboo, Crowd, Crucible and Fisheye Data Center. **Fixed:** Bitbucket **9.4.26 / 10.2.8 / 10.5.1**; Confluence **9.2.26 / 10.2.19**; Jira Software **9.12.40 / 10.3.26 / 11.3.12**; Jira Service Management **5.12.40 / 10.3.26 / 11.3.12**; Bamboo **10.2.24 / 12.1.12**; Crowd **6.3.7 / 7.0.3 / 7.1.7 / 7.2.4**; Crucible and Fisheye **4.9.15**. Atlassian's advisory is still dated **Last modified 5 October** and still says only that its Cloud investigation found no evidence of exploitation, while stating for Data Center that **"Atlassian cannot confirm if your instances have been affected"** — so the vendor page is now behind the facts. **Action: patch today, internet-reachable instances first; if you cannot, remove external access rather than relying on the WAF rule alone.** Then hunt, because exploitation began before most estates patched: **URL-decode access logs up to two passes and search for `..` immediately adjacent to `/`, `\` or `::`**, and search raw log lines for **`::`** inside **`/download/resources/`** and **`/s/.../_/download/`** paths. If `crowd.properties` was readable on any exposed instance, treat the **Crowd application password as compromised — rotate it, and audit `jira-administrators` and equivalent groups for accounts created in the last 72 hours**; that is the specific artefact a successful chain leaves behind. watchTowr has published a **Detection Artefact Generator** on GitHub that checks Jira, Confluence and Bitbucket instances for vulnerability. **Sources:** [watchTowr Labs technical write-up](https://labs.watchtowr.com/you-wont-hear-about-these-even-in-myths-atlassian-jira-confluence-and-more-pre-auth-arbitrary-file-read-cve-2026-21589/) · [Help Net Security](https://www.helpnetsecurity.com/2026/10/07/exploitation-critical-atlassian-flaw-cve-2026-21589/) · [The Hacker News](https://thehackernews.com/2026/10/atlassian-data-center-flaw-draws.html) · [BleepingComputer](https://www.bleepingcomputer.com/news/security/hackers-exploit-critical-atlassian-flaw-after-public-poc-release/) · [Atlassian advisory](https://confluence.atlassian.com/security/cve-2026-21589-arbitrary-file-access-vulnerability-impacts-multiple-products-1870495748.html)

### 1.2 FortiBleed: FBI/USSS advisory on an active campaign with 86,644 Fortinet credentials, and attackers are locking admins out (NEW, ONGOING)

This is not a vulnerability and that is the whole point — the **FBI and US Secret Service** advisory (**IC3 CSA 261006**) describes a Russian-speaking credential campaign against internet-facing **FortiGate firewalls and SSL VPN gateways** that the agencies say **"remains an active threat."** Scale as of **19 June 2026: more than 86,644 working device credentials across 194 countries**, first documented by **SOCRadar** and **Hudson Rock** in June. The exposure is **reused and leaked credentials plus legacy SHA-256 password storage**, which made offline cracking cheap. The five-stage playbook: reconnaissance for exposed portals; initial access by **credential stuffing and password spraying** from leak dumps and infostealer logs; credential capture with **FortigateSniffer**, a Go tool that passively intercepts authentication traffic across **24 protocols**; offline cracking on a GPU cluster with **Hashcat and Hashtopolis**; then lateral movement, Active Directory enumeration, Kerberos validation, SMB authentication, share exfiltration and **stolen session cookies for persistence**. **The operationally urgent part is the destructive turn:** attackers create admin accounts that did not previously exist and, in some cases, **delete or change the passwords of the original accounts, locking the organisation out of its own firewall** (MITRE **T1531**). Access is sold on to initial access brokers supplying ransomware affiliates, with the advisory naming **INC/Lynx** and **Payload** as active buyers — so an admin lockout on a FortiGate is a pre-ransomware indicator, not an IT nuisance. **IOCs:** C2 **45.154.12[.]132**; proxy nodes **154.202.59[.]169** and **103.27.186[.]156**; beacon relay **45.155.250[.]158**. Block with judgement rather than permanently — cloud IPs get reassigned. **Far more useful is the account-name list, which is a five-minute check against any FortiGate admin table: `adminin`, `fortiAdmin`, `forticloud-sync`, `admin`, `fgtsecure`, `pakedge`, `forticloud-tech`, `districtadmin`, `system_config`, `gttadmin`, `roadmin`, `itadmin`, `Technical_support`, `adminsslvpn`, `IT_Manager`, `my_admin`, `support_fortinet`, `fgtsec`, `forti_support2`.** **Action, in order: enumerate local admin accounts on every internet-facing Fortinet device and compare against that list and against your own inventory; terminate all active SSL VPN and administrative sessions (session cookies survive a password reset, which is the defect in the obvious remediation); reset VPN and administrative passwords; migrate administrator passwords to PBKDF2, available on FortiOS 7.2.11 and later; require phishing-resistant MFA for all remote and admin access; and remove internet-facing administration entirely, or restrict it with a local-in policy.** Review logs for AD enumeration and SMB authentication from the appliance. If you find a deleted or renamed admin account, treat it as an active intrusion with a ransomware buyer attached and isolate, collect artefacts and report to the FBI and USSS. **Sources:** [The Hacker News](https://thehackernews.com/2026/10/fbi-warns-fortibleed-remains-active.html) · [Security Affairs](https://securityaffairs.com/200558/cyber-crime/fortibleed-hit-86000-firewalls-by-exploiting-something-nobody-can-patch-away.html) · [BleepingComputer](https://www.bleepingcomputer.com/news/security/fbi-ongoing-fortibleed-attacks-lock-out-fortigate-vpn-admins/) · [Help Net Security](https://www.helpnetsecurity.com/2026/10/07/fortinet-fortibleed-campaign-fbi-advisory/) · [The Register](https://www.theregister.com/security/2026/10/07/fortibleed-still-a-bleeding-nuisance-as-fbi-confirms-ongoing-attacks/5301585)

### 1.3 SonicWall SMA1000 CVE-2026-102255: CVSS 10.0 pre-auth SSRF on a product line already exploited twice this quarter (NEW)

**CVE-2026-102255**, rated **CVSS 10.0** by SonicWall, is a **pre-authentication server-side request forgery** in **WorkPlace**, the SMA1000 user login portal, arising from "an unintended access path." SonicWall says an attacker could "reach internal functionality and perform unauthorized operations" but does not specify which functions — so the ceiling is unestablished and the floor is pre-auth reach into the appliance's internals. **Affected: SMA1000 models 6210, 7210 and 8200v, versions 12.4.3-03526 and older, and 12.5.0-02952 and older. Fixed: 12.4.3-03670 and higher, 12.5.0-03082 and higher.** Three further flaws in the same hotfix: **CVE-2026-102256** (**CVSS 7.8**, OS command injection, admin login required), **CVE-2026-102257** (**CVSS 7.2**, Zip Slip in AMC), **CVE-2026-102258** (**CVSS 5.5**, stored XSS in AMC). ### 1.4 Three ccTLD registries hijacked, 12 rogue TLS certificates issued for Google and YouTube names, other brands affected and unnamed (NEW, significant)

Attackers compromised the **.gh** (Ghana), **.sl** (Sierra Leone) and **.as** (American Samoa) country-code registries, **changed authoritative DNS records**, and used that control to pass domain validation and obtain **12 DV TLS certificates covering seven Google and YouTube names** — **11 from Let's Encrypt, one from ZeroSSL** — logged between **22 and 27 September**. The legitimate baseline for those names, back to at least 10 September, was **Google Trust Services**, so the issuing CA alone was the tell. Certificates were revoked **26 September** (the two .gh and the ZeroSSL one) and **1 October** (the remaining nine); Google has **blocked them in Chrome via CRLSets** and says **its own systems were not breached**. Two things make this bigger than a Google story. First, **Google states it found CT data pointing to other affected organisations — "well-known global brands and widely used online services" — which it has blocked in Chrome and contacted where possible, and has not named — while acknowledging "we cannot guarantee that our analysis identified every affected domain."** Second, the mechanism generalises: a registry compromise defeats domain validation entirely, and **domain-validation reuse is currently permitted for up to 200 days** (falling to 100 days in March 2027 and 10 days in March 2029; Let's Encrypt reuses for 30 days, targeting 7 hours by 2028), so a hijack window of days can authorise issuance long after control is restored. **Unknown: who the attackers are, how the registries were compromised, whether they are now secured, and whether any certificate was actually used to intercept traffic.** **Action: today, enumerate every domain you own — including parked names and regional ccTLD variants of your brand, which is exactly the category nobody monitors — and put them under Certificate Transparency monitoring.** Then **publish a strict CAA record**, and where your CA supports **RFC 8657** account binding, bind it: a CAA record cannot stop issuance during an active DNS hijack, but it blocks later issuance off a reused validation once you have control back, which is the long tail of this attack. If you find a certificate you did not request, file a **Certificate Problem Report** with the issuing CA, which must provide initial findings within **24 hours** under the Baseline Requirements. **IOCs — certificate SHA-256 fingerprints:** `0357032e1214ae11d7da8e00f6b89fb7694e240b17d05f2f47feaf43e96aa7d8`, `8886ca2b71501a6729f1ae868bd7d7b9b53c5cb6b5c7d851d041db4d6206945d`, `986d36b1c68c3e800596c4680dd6c67c42118955e08b472f641793c59dcd347b`, `2e1f6d7f24650b0720636efe48f2ccf59704ee6f11ffa52b5a4c4afcc474fe91`, `e1667fe4e4ea98427960ea2eda7c53af1246ec58ac22282a6877d394a0957065`, `e1e4fd74f673f1df9c039ae6424b36868a0475a043abea2dedd1f6f12a365ebf`, `5b7c491c8784eb438b1634981f1ea6333d3557431268233c2a7a92173ca17122`, `a10d3b5dbc142d040e6ae772ab41dc44b0e94659237709d1241fdefdd36f7b35`, `491f453d208bbb7923626c208df93c95fdfae3b78b738b996c8dafda9d00619a`, `798079c762496d26ce99d3a9113cb24715e31ec8a69a6cdcffa70f5001e19df0`, `607afd2745b84c4332e028262937be35f25316aadf584340269d23a3dbcd37ef`, `b7ea8c77695cf9791a9d45f17c33ebb9bd5f68d4c96df6f56136dc6a834576d2`. **Sources:** [The Hacker News](https://thehackernews.com/2026/10/attackers-hijack-gh-sl-and-as.html) · [Help Net Security](https://www.helpnetsecurity.com/2026/10/07/google-unauthorized-https-certificates-cctld-hijacks/)

### 1.5 Veeam Backup & Replication CVE-2025-64393: CVSS 9.4 RCE on the backup server from a low-privileged account (NEW)

**CVE-2025-64393**, **CVSS 4.0 score 9.4**, is **insecure deserialization of untrusted data** processed through the **Mount Service**, giving **remote code execution on the backup server**. The access requirement is the part to weigh: **an authenticated account holding only the Backup Viewer role** — network vector, low complexity, low privileges, no user interaction. Backup Viewer is the role organisations hand out freely to auditors, service desk staff and reporting users precisely because it is read-only, so the population of accounts that can reach this is larger than the population most teams would consider privileged. **Affected: build 12.3.2.4854 and earlier in version 12. Version 13 is not affected. Fixed: 12.3.2 P4, build 12.3.2.4934, released 6 October.** Reported via **HackerOne**. **No confirmed exploitation and no public PoC or reproduction steps.** Three further CVEs in the same update: **CVE-2026-58069** (**CVSS 8.3**, an authenticated Cloud Connect tenant can read arbitrary files on the service provider host — service providers should treat this as the priority item); **CVE-2026-93026** (**CVSS 6.1**, a Backup Viewer can modify or delete the Enterprise Manager master key and read or overwrite stored antivirus update credentials); **CVE-2025-64392** (**CVSS 4.8**, reflected XSS in Enterprise Manager). **Action:** upgrade to **12.3.2.4934**. In the same window, **audit who actually holds Backup Viewer** and remove it from accounts that no longer need it — this is the cheap structural fix, since two of the four CVEs are reachable from that role. Treat the backup server as a tier-zero asset for network reachability: the Mount Service should not be reachable from general-purpose user segments. Ransomware operators target backup infrastructure first and a deserialization RCE on a Veeam server is exactly the primitive they want, so do not let "no exploitation reported" set the timeline here. **Sources:** [GBHackers](https://gbhackers.com/critical-veeam-backup-replication-flaw/)
