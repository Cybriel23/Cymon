### 1.1 Citrix NetScaler CVE-2026-107406: CVSS 9.5 memory overflow reaching RCE on SAML-configured appliances — the fourth critical in two weeks (NEW)

Citrix published **advisory CTX697191** on **9 October** covering **CVE-2026-107406**, a **memory overflow** in **NetScaler ADC and NetScaler Gateway** rated **CVSS v4.0 9.5 (Critical)**. **Depending on configuration it leads to remote code execution or denial of service** — the RCE outcome is what separates this from **CVE-2026-88779**, the DoS-only memory overflow CISA added to KEV earlier this week. **The precondition is narrow and checkable: only appliances configured as a SAML Service Provider or SAML Identity Provider are vulnerable**, and which of the two applies depends on the software version. **Check with `add authentication samlAction` (SP) and `add authentication samlIdPProfile` (IdP) in your running configuration** — if neither appears, you are not exposed to this one. **Fixed versions: NetScaler ADC and Gateway 14.1-73.46 and later; 13.1-64.29 and later in the 13.1 line; NetScaler ADC 14.1-FIPS 14.1-73.46-FIPS and later; NetScaler ADC 13.1-FIPS and 13.1-NDcPP 13.1.37.283 and later.** **Citrix says it is not aware of any unmitigated exploits or attacks in the wild at publication.** Reported by **Michael Tucker, Chew Keong Tan and Alex Bernier of the JPMorgan Chase XOR Team**, and independently by **Maxim Suhanov**. **The reason to treat this as urgent despite the absence of exploitation is the recent base rate on this exact product: CVE-2026-88771 and CVE-2026-88772 (both CVSS 9.5) were confirmed exploited with custom malware against government, banking and professional-services targets, and CVE-2026-88779 reached KEV with forensic-triage requirements this week.** NetScaler is the appliance class where the gap between advisory and mass exploitation has repeatedly been measured in days, and it sits in front of everything. **Action: today, run the two config greps above across every NetScaler instance and build the list of SAML-configured appliances — that list, not your whole NetScaler estate, is your emergency change scope. Patch those to the versions above this weekend; if an appliance cannot take the upgrade, removing or reconfiguring the SAML authentication action is the only control that removes the precondition, because Citrix publishes no workaround. While you are in there, finish the outstanding NetScaler work this briefing has been carrying: CVE-2026-88779 (14.1-73.41 / 13.1-64.28, deadline expired 7 October) and the CVE-2026-88771/88772 post-exploitation checks — verify `/flash/nsconfig/ns.conf` holds no `sec_monitor` superuser, confirm `/bin/sh` is not mode 6555, and preserve `nsaaad` crash dumps before any restart.** Note that upgrading to the new fixed versions does not evict an attacker who was already resident from the September exploitation wave. **Sources:** [Security Affairs](https://securityaffairs.com/200700/security/cve-2026-107406-citrix-fixes-critical-netscaler-adc-and-gateway-vulnerability.html) · [The Hacker News](https://thehackernews.com/2026/10/citrix-patches-critical-netscaler-flaw.html) · [SecurityWeek](https://www.securityweek.com/citrix-urges-immediate-patching-of-critical-netscaler-vulnerability/) · [The Register](https://www.theregister.com/2026/10/09/citrix_netscaler_critical_patch/)

### 1.2 AhsayCBS: two unpatched flaws chained for unauthenticated SYSTEM RCE, exploited in the wild, and the current release is still vulnerable (NEW, EXPLOITED, NO PATCH)

**Huntress** reports active exploitation of **CVE-2026-105133** and **CVE-2026-105134** in **AhsayCBS**, the centralised backup-server platform used heavily by MSPs and hosting providers. **NIST disclosed both on 4 October after exploit code was released**, and states that **all versions up to 10.3.2** are affected — but **Huntress says the latest version, 10.3.4, is also affected, and there is no patch available**. The chain: **CVE-2026-105134 is an authentication bypass in the Replication Receiver API where a random token substitutes for valid credentials**, which combined with the OS command injection gives **unauthenticated remote code execution with SYSTEM privileges**. Observed tradecraft is a textbook cryptomining intrusion with two details worth noting: the attackers **configured a malicious replication receiver and dropped a JSP web shell into the application directory served by CBS**, then deployed **XMRig cryptominers disguised as Microsoft Edge**, persisted via **a Windows service masquerading as "Microsoft Edge Update" running a renamed NSSM copy (`msedge.exe`) as SYSTEM**, and in one case loaded **`WinRing0x64.sys`** — a legitimate but vulnerable kernel driver — to give the miner kernel-level access. They also deployed **an AI-assisted PowerShell script that watches for Task Manager and kills it if it stays open too long**, which is a small but telling escalation in commodity anti-analysis. **At least five organisations had been targeted as of 8 October.** **Why this outranks most unpatched criticals: AhsayCBS is a backup server. It holds credentials for everything it backs up, it is frequently internet-exposed by design so remote clients can reach it, and it is very often an MSP's shared platform — so one compromise is a tenant-wide compromise.** **Action: there is nothing to patch, so the control is network placement. Today, restrict the AhsayCBS management interface to trusted source IPs or put it behind VPN only — Huntress's own guidance, and the only thing that works. Then hunt, because exploitation predates disclosure: enumerate configured replication receivers and delete any you did not create; search the CBS application directory for unexpected `.jsp` files; check for a Windows service named like "Microsoft Edge Update" whose binary path points at an `msedge.exe` outside the real Edge install location; look for `WinRing0x64.sys` being loaded on a backup server, which has no legitimate reason to exist there; and enable the Microsoft vulnerable-driver blocklist if it is not already on. If you find any of it, treat every credential stored in or reachable from that backup server as compromised, and remember a miner is frequently the cheapest monetisation of an access that was also sold.** **Sources:** [SecurityWeek](https://www.securityweek.com/unpatched-ahsaycbs-vulnerabilities-exploited-in-the-wild/) · [The Hacker News](https://thehackernews.com/2026/10/attackers-exploit-ahsaycbs-flaws-to.html)

### 1.3 GhostAction returns: malicious "Security Audit" workflows now mine the entire git history, so rotating current secrets is not remediation (NEW, significant)

The **GhostAction** campaign — first documented by **StepSecurity in September 2025** — resumed on **8 October** with a materially more damaging payload. Two compromised maintainer accounts pushed a malicious workflow to **345–346 repositories in two automated sweeps**: **`kitao`** (author of **pyxel**, 18,420 stars, publishing to **PyPI and crates.io**) to **27 repositories** between **13:40 and 13:44 UTC**, and **`henrywoo`** to **318 repositories** — **39 sources and 279 forks**, plus the organisation repository **`uber/athenadriver`** where he held write access as original author — in a **16-minute window from 21:10:15 to 21:26:32 UTC**. **Socket reports the wider campaign spans 500+ GitHub accounts and tens of thousands of repositories since 7 October**; **GitGuardian separately counted 772 public repositories across 373 users and organisations between 31 August and 30 September, targeting 2,577 secrets.** The commits appear **under the victims' real identities** with innocuous messages ("Add security audit workflow"), in single-file pushes to the default branch. **The workflow — `security-audit.yml` or `github_actions_security.yml` — triggers on `workflow_dispatch` and on any push to any branch or tag, checks out with `fetch-depth: 0`, and runs one "Audit" step that does four things: appends the repository's named Actions secrets; scans the working tree for 13 credential patterns; scans the full git history via `git log -p --all` for the same patterns; and pairs AWS access key IDs with the secret keys found near them.** The patterns cover **AWS long-term and temporary access key IDs, secret access keys and session tokens; Anthropic, OpenAI project and OpenRouter API keys; GitHub classic and fine-grained tokens and GitLab tokens; and Google/Firebase/GCP API keys, Slack tokens and SendGrid keys.** Exfiltration is a single **HTTP POST in cleartext to the hardcoded IP `193.32.204[.]199`**; StepSecurity confirmed one run where **the attacker's server acknowledged the data four seconds after the workflow started**. **The history sweep is the change that matters. Every remediation playbook for a stolen CI secret says "rotate the Actions secrets" — and that is now insufficient, because a credential committed in 2021 and deleted in 2022 is still in the object store and was still exfiltrated.** The fork exposure is the second trap: **279 of the affected repositories are forks in the `henrywoo` namespace**, and any fork owner who enables Actions and pushes will run the workflow against **their own** history and send the results to the same collector — which is how this reaches organisations with no relationship to either maintainer. **No malicious package releases had been published using the stolen publishing credentials as of writing**, and in one repository an **approval requirement for workflow runs stopped execution outright** — the single control that demonstrably worked. **IOCs: workflow paths `.github/workflows/security-audit.yml` and `.github/workflows/github_actions_security.yml`; commit messages "Add security audit workflow", "Update security audit workflow", "Add Github Actions Security workflow"; request markers `REPO=`, `AKIA_CTX_START`, `AKIA_CTX_END`; C2 `193.32.204[.]199`.** **Action, in order: block and hunt `193.32.204[.]199` in egress logs including from self-hosted runners; search every repository you own, and every fork you have taken from an affected namespace, for those two workflow filenames dating back to 31 August 2026. Where present, treat it as a confirmed breach and rotate every credential ever committed to any branch — not only current Actions secrets — scanning unreachable objects too, and check CloudTrail and IAM for any AWS keys found. Revoke the implicated account's sessions, tokens, OAuth grants and SSH keys and re-enrol it on phishing-resistant MFA, review PyPI, crates.io, npm and container-registry release history for versions you did not publish, and hold releases until cleanup completes. Structurally, the two controls worth landing this quarter are requiring approval for workflow runs and branch protection with PR review on `.github/workflows/` — the one repository that survived did so because of the first.** Note this is **distinct from the `tensorlake` Shai-Hulud worm** in §2, though the two together make this the worst week for GitHub-identity supply-chain attacks this briefing has recorded. **Sources:** [StepSecurity](https://www.stepsecurity.io/blog/ghostaction-returns) · [Socket](https://socket.dev/blog/ghostaction-cloud-credentials) · [The Hacker News](https://thehackernews.com/2026/10/credential-stealing-github-actions.html) · [GitGuardian](https://blog.gitguardian.com/ghostaction-github-actions-supply-chain-attack-returns/)

### 1.4 Public pre-auth root exploit for AnyDesk on Linux, against a flaw silently fixed in June and never assigned a CVE (NEW)

Researchers from the **V12 security team** published a working exploit called **AnyPwn** on **GitHub on 8 October** for a **pre-authentication heap buffer overflow in AnyDesk for Linux** that yields **arbitrary command execution as root**. **There is no CVE as of 9 October and AnyDesk has issued no security advisory.** The technical shape is clean and unpleasant: **the session protocol's mode-5 stream packet handler adds a 16-byte header to the attacker-declared payload length using unchecked 32-bit arithmetic, so a declared length of `0xFFFFFFF0` wraps to a tiny allocation and even a single byte of attacker data writes past the buffer**; the exploit drives a ROP chain to run a command as root. **The code path is reachable before the incoming connection is approved** — no user interaction, no credentials. **The published exploit targets AnyDesk Linux 8.0.2 over direct TCP connections on port 7070**; the researchers suggest **8.0.1 and earlier may share the vulnerable path** but have not confirmed it, and they validated that **the same path is reachable through AnyDesk's relay servers** using a Frida trigger without building a full remote chain. **Windows and macOS are not affected per AnyDesk.** **The fix shipped in 8.0.3 in June 2026, described in the changelog only as "fixed a bug that could lead to a crash"** — which is the whole governance lesson here, because an estate that patches on advisory severity had no reason to prioritise 8.0.3 and has therefore been exposed for four months. The current release is **8.1.0**. Exploitation is **probabilistic**: a failed heap layout crashes the service instead of executing, so attempts are noisy. **No confirmed in-the-wild exploitation is reported.** **Action: inventory AnyDesk on Linux hosts — jump boxes, build servers, kiosks and engineering workstations are where it hides — and upgrade to at least 8.0.3, preferably 8.1.0, today. Where an immediate upgrade is impossible, restrict inbound TCP/7070 to known management ranges, and note that this only reduces exposure because the relay path appears reachable too. Then hunt for the failure mode rather than the success: repeated unexplained crashes or restarts of the AnyDesk service on a Linux host are now a credible indicator of attempted exploitation, so check journald and any crash-dump retention before it ages out. More broadly, this is the argument for treating remote-access agents as perimeter software with their own patch SLA regardless of whether the vendor calls a release a security fix.** **Sources:** [The Hacker News](https://thehackernews.com/2026/10/researchers-publish-working-exploit-for.html)
