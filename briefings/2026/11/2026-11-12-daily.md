# Daily Cyber Threat Intelligence Briefing
Thursday, 12 November 2026 · Coverage: 06:00 UTC 11 Nov – 06:15 UTC 12 Nov 2026 and follow-ups on tracked topics

## Executive Summary
The day after Patch Tuesday was busy, and the main risk was in managed-service-provider (MSP) tooling. CISA added nothing to KEV on 11 Nov. Three things need attention today. **First**, a worm-like campaign called **SCKit** is using compromised cloud-hosted ConnectWise ScreenConnect panels to install rogue clients. Huntress counts at least **288 endpoints in 48 organizations** and says the number is rising. ConnectWise has disabled five third-party extensions in about **400** partner environments. **Second**, N-able has released **N-central 2026.4 HF2**, which fixes the most serious Able2Shell flaws. Proof-of-concept code for all **33** issues is public and honeypots are already seeing exploitation attempts, so on-premises servers should be upgraded before they are brought back online. **Third**, **CVE-2026-119618** in Apache HTTP Server's mod_http2 is a pre-authentication RCE rated 9.8 by Red Hat. It is fixed in **2.4.71**. Separately, Vates has corrected the fixed versions for the exploited Xen Orchestra bypass and disclosed a second zero-day that is not yet patched. KEV deadlines for SSHole, GPUStack, FreeSWITCH and Aspera Faspex are **today**, and the Barracuda ESG chain is due **tomorrow (13 Nov)**. Watch this week for: how ScreenConnect panels were accessed and whether new IOCs appear; N-able's follow-up hotfix and any confirmed in-the-wild exploitation; a Vates patch for the VM-import zero-day; Ubuntu and other distribution builds of httpd 2.4.71; whether Maersk confirms what the WhiteArmor data contains; and a Microsoft response to the SignDrop CLFS claim.

## 1. Risk Watch

### 1.1 ConnectWise ScreenConnect "SCKit" worm hits MSPs: 288+ endpoints, 48 organizations (NEW, ONGOING)
- **What is happening:** starting about **17:47 UTC on 11 Nov**, attackers used compromised cloud-hosted ScreenConnect panels and their **Run Command** feature to install rogue ScreenConnect clients on managed endpoints. This gives them access that no longer depends on the MSP's own panel. Huntress counts **six compromised MSPs** and at least **288 endpoints across 48 organizations**. Attacker-assigned tags are sequential, which suggests earlier MSP victims.
- **Initial access:** not yet established. Huntress says its telemetry points to stolen credentials or hijacked operator sessions, not a new vulnerability. ConnectWise suspects that **independent third-party extensions** exposing a remote-command API were abused. It has disabled five of them across about **400** partner environments. On-premises customers must disable them manually.
- **Tooling:** the dropper `sckit-run.bat` fetches `sckit-decoder.ps1`. The toolkit adds Defender exclusions, installs a second attacker-controlled ScreenConnect client, creates a scheduled task named **`TrapWatch`**, and replaces the legitimate installation.
- **Designed but not yet seen working:** a worm stage that spreads to a technician's workstation when they connect to an infected endpoint. It steals the `.aspxauth` cookie, replays it to the panel, and pushes a SYSTEM payload (`WithUninstall.ps1`) to every reachable session through the Shared Toolbox using `ToolboxRelayUploader.exe`. Huntress has not yet observed a successful jump.
- **Precedent:** like the 2024 ScreenConnect "SlashAndGrab" attacks, one compromised RMM panel gives access to every downstream customer.

**Action:**
- **Disable** the third-party extensions that ConnectWise names, and do not reinstall them.
- **Review** Run Command history, Toolbox items, extension installs, new admin accounts and sign-ins, even if you have had no alerts.
- **Hunt** endpoints for unknown ScreenConnect client IDs, the `TrapWatch` task, Defender exclusions, and `sckit-*`, `Panel-Lateral.ps1` and `LabConfig.ps1`.
- **Block** these IOCs:
  - relay `185.99.255[.]28`;
  - C2 `newnewnew.gotdns[.]org`, `soxnewwork.homedns[.]org`, `sc.payproofkit[.]com` (`155.94.150[.]39`), `ns.mo7sen[.]dev`;
  - possible C2 `cdn007-digitaldownloads[.]com`.
- **Avoid** opening interactive ScreenConnect sessions to suspect hosts; investigate them with separate tools.
- **Rotate** technician credentials and session tokens, and enforce MFA on panels.

Sources: [Huntress](https://www.huntress.com/blog/sckit-worm-rogue-screenconnect), [BleepingComputer](https://www.bleepingcomputer.com/news/security/active-screenconnect-attacks-breach-msps-impact-dozens-of-organizations/), [The Hacker News](https://thehackernews.com/2026/11/screenconnect-attacks-target-at-least.html)

### 1.2 N-able N-central Able2Shell: HF2 released, hosted back online, PoCs for all 33 issues public (follow-up, ONGOING)
- **The fix:** N-central **2026.4 Hotfix 2 (build 2026.4.1.26)** fixes seven CVEs. These are N-able's "most critical" issues from the Able2Shell disclosure:
  - **CVE-2026-125883** (XXE);
  - **CVE-2026-125878** (OGNL injection);
  - **CVE-2026-125879** (root privilege escalation through a syslog-ng config);
  - **CVE-2026-125880** (stored XSS);
  - **CVE-2026-125881** (SSRF);
  - **CVE-2026-125882** (RCE through upload path traversal);
  - **CVE-2026-91000** (insecure IPC leading to local privilege escalation).
- **What HF2 changes:** it temporarily **disables built-in remote control**. N-able has promised a follow-up hotfix. It has not said how the seven CVEs map to the 33 published issues.
- **Status:** all hosted (NCOD) servers have been upgraded and are back online.
- **Exploitation:** N-able has not flagged any in-the-wild exploitation.
  - Defused saw probing, including anonymous agent sessions, appliance-config pulls and unauthenticated remote-control requests.
  - watchTowr saw exploitation attempts against its N-central honeypots.
  - Shadowserver's count of exposed servers fell from **1,338** to about **148**.
- **Disclosure dispute:** the researcher, Sean Bales, now confirms he did not report the flaws to N-able before publishing.

**Action:**
- Upgrade on-premises N-central to HF2 **before** reconnecting it, then update agents and probes.
- Keep the management interface off the internet.
- Before restoring access, check for:
  - new or changed admin accounts (especially "Default Administrator" resets);
  - unexpected scripts or automation policies pushed to devices;
  - files written under the file-repository path since **8 Nov**.
- Expect a second hotfix, and treat any of the 33 issues not mapped to a CVE as possibly still open.

Sources: [BleepingComputer](https://www.bleepingcomputer.com/news/security/n-able-releases-security-hotfixes-for-zero-day-vulnerabilities/), [Infosecurity](https://www.infosecurity-magazine.com/news/n-able-n-central-able2shell-0day/), [Dark Reading](https://www.darkreading.com/endpoint-security/n-able-n-central-offline-33-flaws)

### 1.3 Apache HTTP Server mod_http2 CVE-2026-119618: pre-authentication RCE, fixed in 2.4.71 (NEW)
- **The flaw:** **CVE-2026-119618** in **mod_http2** affects **httpd 2.4.55–2.4.70** and standalone **mod_h2 2.0.8–2.0.42**. It is fixed in **2.4.71**, released 11 Nov.
- **Severity:** Red Hat rates it **9.8**, an unauthenticated flaw that can give control of the server process. It says public research has shown a "reliable exploit" against the default configuration, but it did not link that research. Wiz says no public exploit or in-the-wild exploitation has been reported.
- **Who is affected:** only servers with `h2` or `h2c` enabled in a `Protocols` directive, set either server-wide or per virtual host.
- **Distributions:**
  - RHEL 9 and 10 have fixes (e.g. `mod_http2-2.0.26-7.el9_9.1`). Red Hat rates the flaw Important there because of per-stream allocators.
  - RHEL 8 and earlier are not affected.
  - Debian and Amazon Linux are tracking it.
- **No fix coming for mod_h2:** the standalone project was archived in June and has no fixed release.
- **Also in 2.4.71:** a crash in mod_md and a one-byte stack overwrite in mod_vhost_alias.
- **Credit:** Anthropic's OSS Scanner and Google Cloud Vulnerability Research reported the flaw independently.

**Action:**
- Find every httpd instance with HTTP/2 enabled, including reverse proxies and appliances that embed Apache.
- Upgrade to 2.4.71 or your distribution's fixed package.
- Where you cannot upgrade yet, drop `h2`/`h2c` so that `Protocols http/1.1` remains. Do this on every vhost as well as server-wide.
- Replace standalone mod_h2 builds.

Sources: [Apache httpd security advisory](https://httpd.apache.org/security/vulnerabilities_24.html), [The Hacker News](https://thehackernews.com/2026/11/critical-apache-http2-flaw-could-let.html), [Cyber Security News](https://cybersecuritynews.com/apache-patches-critical-http-2-flaw/)

### 1.4 Xen Orchestra: corrected fixed versions and a second, unpatched zero-day (follow-up, ONGOING)
- **Corrected versions:** Vates now says the exploited REST authentication bypass (the empty-object `authenticationToken` cookie, reported here yesterday) is fixed in **Xen Orchestra 6.9.2 (stable)** and **6.10.1 (latest)**. Instances updated only to 6.9.1/6.10.0 should be upgraded again, and the XO Appliance is also affected.
- **Second zero-day:** the same actor has exploited it. It needs **admin** rights and abuses **malicious VM imports** to compromise XCP-ng hosts. **No fix yet.**
- **Logging and IOCs:** unauthorized access is not logged. Vates says its IOCs (**91.211.251[.]112:8001**, Tor) cover only this campaign, so finding none does not rule out compromise.
- **Still no CVE.**

**Action:**
- Upgrade to 6.9.2/6.10.1 and put XO on a dedicated management network.
- Keep the WAF rule that blocks the empty token.
- Restrict VM imports to trusted sources and roles until the zero-day is fixed.
- Rotate all XO and host credentials.
- On confirmed compromise, **fully reinstall**. Vates says cleanup alone cannot guarantee that backdoors are removed.
- Yesterday's hunting artifacts still apply (`pivot2` VM, `/etc/cron.d/zz-ustar*`, `/.ustar5`/`/.ustar6`).

Sources: [SecurityWeek](https://www.securityweek.com/critical-xen-orchestra-flaws-exploited-in-attacks/), [The Hacker News](https://thehackernews.com/2026/11/hackers-exploit-critical-xen-orchestra.html)

### 1.5 Node.js: 16 fixes, including an HTTPS memory leak that can expose TLS private keys (NEW)
- **Fixed versions:** **v22.23.5, v24.22.3 and v26.13.1** fix **16** CVEs (7 high), with updated llhttp, undici and sqlite.
- **Most serious, CVE-2026-123864:** an unauthenticated client can make an HTTPS server copy freed heap memory into a request body. That memory may hold **TLS private keys** or other users' requests.
  - **Exposed:** handlers that call `res.flushHeaders()` early and later end with a non-empty chunk, where the route echoes or stores bodies.
  - **Not affected:** plain `node:http`.
- **HTTP/2 flaws:**
  - **CVE-2026-123863**: an unauthenticated abort, a variant of CVE-2024-27983.
  - **CVE-2026-123874/-123875**: `respondWithFile()` memory corruption and crash.
  - **CVE-2026-123866**: leaks freed response memory.
- **mTLS bypasses:**
  - **CVE-2026-123872**: SNI switching during TLS 1.2 renegotiation.
  - **CVE-2026-123867**: a per-host CA falls back to the default CA.
  - **CVE-2026-123877**: TLS session reuse in `https.Agent`.
- **Exploitation:** none reported. Five of the flaws were found with AI assistance.

**Action:**
- Upgrade internet-facing HTTPS and HTTP/2 services first, then rebuild container images.
- Move off end-of-life lines.
- If a vulnerable HTTPS handler served untrusted traffic, consider rotating its TLS keys, because the leak leaves no trace.

Sources: [Cyber Security News](https://cybersecuritynews.com/node-js-fixes-16-security-vulnerabilities/), [GBHackers](https://gbhackers.com/node-js-patches-16-security-vulnerabilities/)
