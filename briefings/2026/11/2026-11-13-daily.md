## 1. Risk Watch

### 1.1 N-able N-central "4EverAble2Shell": exploited against Hotfix 2 servers, Legacy API is the gate (NEW, ONGOING)
On **12 Nov**, researcher Sean Bales published two new PoCs that he tested against **N-central 2026.4.1.26 (HF2)**. N-able released HF2 on 10 Nov.
- **4EverAble2Shell (unauthenticated root RCE):** chains Apache Axis **CVE-2026-90436** (CVSS **9.8**, unsafe class instantiation in SOAP fault handling, which gives code execution as the `nable` account) with a local privilege escalation. The escalation abuses the `setLDFileOwner` helper and a symlink, then `serverControl`, to run commands as root. Previdian tracks it as VULN-2026-0009. It works only when the **Legacy API** is enabled.
- **Agent2Shell:** claims SYSTEM on managed Windows agents under specific conditions.
- **Exploitation:**
  - Probing from **157.20.241[.]16** began at about **08:30 UTC**, and full chains followed from **09:16 UTC**.
  - Huntback counted **21** live XMRig miners (worker names `nc_*`, using half the CPU cores) on N-central hosts in the US, CA, ZA, UK, DE, FR and SE. **19** of them were on HF2.
- **N-able's response:**
  - It says it has seen no compromise, and that hosted servers are not vulnerable.
  - It has turned off the Legacy API and the **Intune integration** on hosted servers.
  - It promises further remediation, but there is no fixed build yet.
  - Bales also says two RCEs in another N-able product, reported in July, remain unpatched.

**Action:**
- **On-premises:** confirm the Legacy API is disabled (it is off by default), upgrade agents **and** probes to HF1/HF2 or later, and keep the console off the internet.
- **Hunt:**
  - outbound connections to `157.20.241[.]16:8080`;
  - `jup.sh`, `mount -o remount,exec /tmp`, xmrig processes and pool connections;
  - files changed by `setLDFileOwner`/`serverControl`.
- **On a hit:** rebuild the server and treat every managed endpoint as exposed. Huntback notes that the miner is the only payload seen so far, but it runs as root on a host that manages customers' endpoints.

Sources: [BleepingComputer](https://www.bleepingcomputer.com/news/security/new-n-able-4everable2shell-zero-day-exploited-hours-after-poc-released/), [The Hacker News](https://thehackernews.com/2026/11/hackers-exploit-n-central-flaws-to.html), [Huntress](https://www.huntress.com/blog/n-able-disables-cloud-services-following-disclosure-of-able2shell-exploit-chains), [SecurityWeek](https://www.securityweek.com/hackers-target-n-central-zero-days-as-n-able-rushes-patches/)

### 1.2 Check Point Mobile Access: PHP2Shell plus CVE-2026-123039 used to deploy a backdoor and an ESXi wiper (NEW)
Check Point Research (CPR) confirms exploitation of unpatched Security Gateways with **Mobile Access** portals. The attacks started about one week after Check Point released the fix.
- **Waves:**
  - **30 Oct:** aimed at Israeli organizations, from **130.94.19[.]204**, with destructive activity at some victims.
  - **2 Nov:** a broader, opportunistic wave across many countries and sectors, with no destruction seen.
- **Chain:**
  1. PHP **CVE-2026-109618/-109619** (PHP2Shell) for initial access.
  2. **CVE-2026-123039**, a privilege escalation in the DynamicCLI IPC interface, to get root.
  3. `zz*.tpl` PHP webshells (key `zz2026`) in the portal's login templates.
  4. The **TSGA** backdoor (`/tmp/CPconfigdaemon`, which relaunches as `slot_CPconfigdaemon`) with **TSProxy** (`/lib/libcpfwcommon.so`) hooked into appliance processes.
  5. The `gogo` scanner.
  6. SSH to **ESXi** as `vpxuser`.
  7. The **destroy_v6** wiper, which leaves a `DREAM_ANNEXATION.txt` note.
- **Attribution:** TSGA and TSProxy are PhiliKit variants, malware previously tied to China-nexus **UNC5221**'s Ivanti intrusions. CPR does **not** attribute the activity with confidence. It names three possibilities: a broker handing off access, a false flag, or a wiper used to cover the intrusion.

**Action:**
- Apply Check Point's PHP2Shell and DynamicCLI fixes to every gateway running Mobile Access.
- Hunt for:
  - `upload_progress_pwn` session files under `/opt/CPcvpn-R81.20/tmp/`;
  - bursts of Apache/PHP segfaults;
  - `zz*.tpl`, `challenge_render.tpl` or `/tmp/.up.tpl`;
  - `/lib/libcpfwcommon.so` and `/tmp/.bd.log`.
- Rotate the vCenter `vpxuser` and ESXi credentials that the gateways can reach, and restrict SSH from gateways to ESXi.
- Treat any webshell hit as root compromise of the appliance.

Sources: [Check Point Research](https://research.checkpoint.com/2026/php2shell-exploitation-on-check-point-gateway/)

### 1.3 "wfx-loot": 4,837 hijacked GitHub accounts steal CI/CD and cloud secrets (NEW)
- **Timeline:** starting about **12:45 UTC on 10 Nov**, an attacker used stolen credentials for **4,837** GitHub accounts to probe **61,764** repositories for write access. Aikido confirms secrets were stolen from at least **1,835** targets.
- **Accounts affected:** some belong to Fortune 100 companies, US **GSA**, the French government, Nextcloud and WebdriverIO. About 50 of the accounts can publish to npm, PyPI, Go, crates or Packagist.
- **Method:**
  1. Probe pull requests titled **"docs: dependency audit notes"**. **92%** are still open.
  2. A 1,500-line stealer injected through a modified workflow, a new workflow on a short-lived **`wfx-docs`** branch, or an npm install hook.
  3. Theft of Actions secrets, `GITHUB_TOKEN`, OIDC and runtime tokens, AWS, Azure and GCP credentials (including runner IMDS), and SSH, Docker, Kubernetes, npm, PyPI, Vault, Terraform and AI-tool keys.
  4. OIDC-to-cloud exchange and IAM-role chaining to create long-lived credentials.
  5. In under a minute, the attacker reverted the changes and deleted runs and logs.
- **Packages poisoned:** automated publishing pushed the payload into Packagist `digitalelvis/neuronai-studio` **3.14.3** and the Go module `github.com/onuragtas/docker-env` **v1.0.278/v1.0.280**.
- **Precedent:** Aikido notes overlaps with **GhostAction** (2025).

**Action:**
- Search your organization for the PR title, `wfx-docs` branches, and **gaps in workflow run numbers**, which are evidence of deleted runs.
- Where the payload ran, rotate every secret and cloud role that workflow could reach, and review IAM users and trust policies created since **10 Nov**.
- Enforce SSO with MFA and fine-grained PATs, and require approval before workflows run on PRs from contributors.

Sources: [BleepingComputer](https://www.bleepingcomputer.com/news/security/hackers-compromise-4-800-github-accounts-to-steal-cloud-credentials/), [The Hacker News](https://thehackernews.com/2026/11/4837-hijacked-github-accounts-ran-ci.html), [SecurityWeek](https://www.securityweek.com/attacker-targets-60000-github-repositories-in-credential-theft-campaign/)

### 1.4 ScreenConnect SCKit: access traced to the RMM+ extension's blank-key bypass (follow-up, ONGOING)
- **How the attackers got in:**
  - Huntress now ties initial access to the third-party **RMM+** extension. Versions **1.0.31 and 1.0.32** accept an **empty shared access key** when an admin never set one. That let attackers run commands through the API with no ScreenConnect login or MFA, which fits the commands Huntress saw that had no matching user sessions.
  - ConnectWise has narrowed its initial list of five extensions to the RMM+ family and disabled it in about **400** partner environments. It warns that disabling the extension does not remove persistence that is already in place.
- **Spread to technicians:** SCKit's technician-infection stage, RelayTrap (C# source compiled on the host, apparently LLM-generated), targets the client file-transfer flaw **CVE-2026-84869**, which is fixed in **26.6.5**. Blackpoint and Huntress both say the patch blocks it, and no worm hop has succeeded so far.
- **Scope:** unchanged at **288 endpoints in 48 organizations**, all hit within 90 minutes.

**Action:**
- Verify that RMM+ is disabled, especially on-premises, where ConnectWise cannot disable it for you.
- If you must keep the extension, set a strong access key.
- Make sure every technician's ScreenConnect client is on **26.6.5 or later**.
- Keep hunting yesterday's IOCs (the `TrapWatch` task, rogue client IDs, `sckit-*`).
- Do not open interactive sessions to suspect hosts.

Sources: [BleepingComputer](https://www.bleepingcomputer.com/news/security/new-worm-like-sckit-malware-targets-msps-in-screenconnect-attacks/), [The Record](https://therecord.media/connectwise-screenconnect-breaches-third-party-tool), [CyberScoop](https://cyberscoop.com/connectwise-screenconnect-sckit-attack/)

### 1.5 Windows "SignDrop" CLFS privilege escalation: PoC independently reproduced, no patch (follow-up, developing)
- **The exploit:** MSNightmare's PoC abuses CLFS log-file authentication. When a privileged process opens a log prepared by a user, the driver creates the companion `.cnpf` file in the **privileged** process's security context. The PoC redirects that file with object-manager symlinks to get a SYSTEM-created file that the user can write.
- **Trigger:** in the PoC, the Defender update interface, so Defender must be enabled.
- **Affected configurations:** authentication mode **0 (enforced) or 1 (learning)**, which is the default on established Windows 11 25H2/26H1/26H2 and Server 2025 installs.
- **Independent check:** 78researchlab (PurpleHound) reproduced it. It judged the exploit not yet reliable enough for operational use, and it is noisy (it hijacks UAC prompts).
- **Status:** there is no CVE and no Microsoft confirmation or fix. Ten CLFS bugs are already in KEV, one of them used by ransomware.
- **Do not disable the mitigation:** turning CLFS authentication off (registry values 2 or 3) reopens older memory-corruption bugs.

**Action:**
- Add EDR detections for:
  - object-manager symlink creation by standard users;
  - unusual `.blf`/`.cnpf` creation in user-writable paths;
  - Defender update calls followed by SYSTEM shells.
- Prioritize detection on shared and multi-user hosts.

Sources: [The Hacker News](https://thehackernews.com/2026/11/new-signdrop-zero-day-exploit-turns.html), [BleepingComputer](https://www.bleepingcomputer.com/news/security/new-windows-signdrop-zero-day-gives-hackers-system-privileges/)
