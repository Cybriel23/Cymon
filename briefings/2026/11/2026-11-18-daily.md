## 1. Risk Watch

### 1.1 Java4Shell, OpenJDK Base64 decoder RCE (CVE-2026-114938) in Jira, Jenkins, Keycloak and more (NEW)
Calif.io disclosed a heap overflow in the AVX-512 VBMI-accelerated `java.util.Base64` decoder. A malformed string that ends in an extra `=` makes the decoder write **62 to 63 bytes** past its output buffer before the input is rejected. Base64 is often decoded before authentication (Basic auth headers, SAML artifacts, CSRF tokens), so the flaw can be reached remotely. Scores differ by vendor: CVSS 4.0 **9.2** (Calif/Talos), Oracle **8.1**, Red Hat preliminary **9.8**. Affected versions are Java **17.0.6 and later**, plus **21, 25 and 27**, but only on x86-64 CPUs with AVX-512 VBMI: Intel Ice Lake, Sapphire, Emerald and Granite Rapids, and AMD Zen 4 or newer. Standard Java 8/11 and ARM64 are not affected. Calif names **Keycloak, Jira, Confluence, JFrog Artifactory, Jenkins and PingFederate** as reachable without login, and Kafka, Solr, Elasticsearch, Gerrit and Spinnaker as reachable after login. It also says a Java client connecting to a malicious TLS server can be compromised. Calif is withholding its RCE exploits. Other labs have reproduced crashes and a memory leak ("JavaBleed") but not code execution. However, a crash trigger has been public since **9 Sep** in a closed OpenJDK pull request (#32781). Talos and Canada's Cyber Centre are not aware of any exploitation. Fixed builds: Oracle **17.0.21.1 / 21.0.13.1 / 25.0.5.1 / 27.0.1.1**, Corretto **17.0.21.1.2 / 21.0.13.1.2 / 25.0.5.1.2 / 27.0.1.1.4**, and Azul Zulu **17.70.201 / 21.54.201 / 25.38.201 / 27.30.201**. Red Hat, Temurin, Microsoft Build of OpenJDK and Liberica fixes were still pending at the time of reporting.
**Action:** find JVMs on AVX-512 VBMI hosts (`grep -m1 '^flags' /proc/cpuinfo` must show avx512f, avx512bw, avx512vbmi and bmi2), starting with internet-facing IdP, CI and ticketing systems. Patch where fixed builds exist. Elsewhere, start the JVM with **`-XX:-UseBASE64Intrinsics`** (or `-XX:UseAVX=2` on x86-64 only), then restart services and rebuild container images. Do not use `-XX:DisableIntrinsic=_base64_decodeBlock`, which stops Java from starting. To hunt, look for Base64 tokens of 32 or more characters ending in `=` whose length is not a multiple of 4, especially in `Authorization` headers. Also look for bursts of `IllegalArgumentException` from `java.util.Base64$Decoder` and for unexpected `hs_err_pid` crash logs or restarts.
**Sources:** [Cisco Talos](https://blog.talosintelligence.com/java4shell/), [The Hacker News](https://thehackernews.com/2026/11/java4shell-cve-2026-114938-enables-pre.html), [The Register](https://www.theregister.com/security/2026/11/18/oracle-reveals-fix-this-asap-grade-java4shell-bug-that-allows-attacks-on-many-third-party-apps/5310661), [BleepingComputer](https://www.bleepingcomputer.com/news/security/critical-java4shell-flaw-allows-rce-attacks-on-major-java-applications/)

### 1.2 Apache HTTP Server mod_http2 CVE-2026-119618 actively exploited (NEW, ONGOING)
The flaw is a race condition in mod_http2's `assign_headers()` that can corrupt the heap and potentially allow unauthenticated RCE. It affects httpd **2.4.55 to 2.4.70** with mod_http2 enabled, and standalone mod_h2 **2.0.8 to 2.0.42**. Apache rates it critical, and Singapore's CSA scores it CVSS **8.1**. The fix is **2.4.71**, released on 11 Nov. It was reported by Anthropic's OSS scanner and, independently, by Google Cloud researchers. On **17 Nov**, CSA alert AL-2026-164 said the flaw "is reportedly being actively exploited" and that a PoC is public. CSA gave no victim details, and the flaw was not in CISA KEV as of the 17 Nov catalog.
**Action:** upgrade to **2.4.71** or to your distro's fixed package, including on appliances and container base images that bundle httpd. If you cannot patch yet, set `Protocols http/1.1` and confirm that no vhost still offers `h2`/`h2c`. Review recent worker crashes and segfaults in error logs as possible exploitation signals.
**Sources:** [CSA Singapore AL-2026-164](https://www.csa.gov.sg/alerts-and-advisories/alerts/al-2026-164), [Cybersecurity News](https://cybersecuritynews.com/apache-http-server-rce-exploitation/)

### 1.3 Microsoft `agent-framework` PyPI package trojanized: versions 1.26.1 / 1.26.2 steal cloud and CI credentials (NEW)
On **17 Nov**, someone using Microsoft's PyPI publishing identity uploaded two malicious releases: **1.26.1** at **20:35 UTC** and **1.26.2** at **21:08 UTC**. The second upload came **2 min 23 s** after PyPI quarantined the first, so the attacker still had publishing access at that point. Both versions drop a `.pth` startup hook (`agent_framework_meta.pth`/`_telemetry.py`, then `af_runtime_diag.pth`/`af_runtime_diag.py`). The hook runs every time Python starts, even if the package is never imported, and forks a detached collector. It harvests secret-like environment variables, Azure CLI token caches, `.netrc`, `.pypirc`, `.npmrc`, Git, Docker and Hugging Face credentials, Azure DevOps agent files, `.env` files and `/proc` environments. It also tries to mint fresh tokens from GitHub Actions OIDC (1.26.2 only), Azure DevOps OIDC and Azure managed identity. Data is sent in a single POST to `webhook.site` with User-Agent `runtime-diagnostics/1` (`af-runtime-diagnostics/1` in 1.26.1). The uploads were wheel-only, carried no provenance attestations and used uploader UA `RestSharp/106.13.0.0`. Wiz found no matching tag or malicious code in Microsoft's GitHub repository, so the access vector is unknown. Microsoft has not commented publicly. This is at least the second compromise of a Microsoft package registry identity in 2026 (durabletask in May).
**Action:** search lockfiles, caches, mirrors and images for `agent-framework==1.26.1/1.26.2`, and pin **1.26.0** with hashes. On any host or runner that installed either version, isolate it *before* running Python or pip again, because starting the interpreter re-triggers the hook. Rebuild the host and rotate every credential the payload could read or mint: CI secrets, cloud keys, registry and Git tokens, and service connections. Also review OIDC federated-credential trusts and managed-identity role assignments. Hunt egress logs for `webhook.site` and the User-Agents above.
**Sources:** [StepSecurity](https://www.stepsecurity.io/blog/microsoft-agent-framework-pypi-package-compromised), [Endor Labs](https://www.endorlabs.com/learn/agent-framework-compromised-software-supply-chain-attack), [Socket](https://socket.dev/blog/agent-framework-pypi-package-compromised-with-credential-stealer)

### 1.4 Puppet Enterprise / Puppet Server CVE-2026-115731 added to CISA KEV (NEW, deadline 1 Dec)
CISA added this Puppet Enterprise deserialization flaw to KEV on **17 Nov**, with a federal due date of **1 Dec**. It was disclosed on 3 Nov and rated CVSS **9.4**. It affects Puppet Server and the OpenVox fork, and allows code execution on the server through a malicious report. A public PoC based on the OpenVox advisory is circulating. Exploitation requires a client that holds a CA-signed agent certificate, so autosigning setups without strong verification are the most exposed. Fixed in Puppet Enterprise **2023.8.13, 2025.12.1 and 2026.0.1**. Third-party trackers still show "not exploited", but CISA's listing indicates evidence of exploitation.
**Action:** upgrade Puppet Enterprise and Puppet Server or OpenVox now. Disable naive or open autosign (`autosign.conf` wildcards) and review recently signed certificates for unknown nodes. Hunt for unexpected child processes of the puppetserver JVM. A compromised configuration-management server gives the attacker the whole fleet.
**Sources:** [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog), [OpenCVE](https://app.opencve.io/cve/CVE-2026-115731), [SecurityOnline](https://securityonline.info/puppet-server-rce-cve-2026-115731-poc/)

### 1.5 ScreenConnect: ConnectWise disables five third-party extensions as SCKit attacks continue (follow-up, ONGOING)
ConnectWise says it has finished its investigation and disabled **five third-party extensions** across about **400** partner environments: Labtech Plus, RMM Plus, RMM+, RMM Plus Password Link and RMM+ Password Link. Huntress and Blackpoint suspect that an auth flaw in **RMM+ 1.0.31/1.0.32** let attackers run commands without passing ScreenConnect authentication. Attacks continue against on-prem servers that still have these extensions enabled or are not updated. Huntress also logged an SCKit spike on **13 Nov** that hit **205 hosts across 41 organisations**. SCKit's RelayTrap module uses **CVE-2026-84869** (CVSS 9.9) to jump to technician workstations. IOCs: rogue client hosted at `185.241.211[.]197` (1337 Services GmbH), and persistence through a "Windows Update Agent" service running `UpdateConnect.ClientService.exe` from `C:\ProgramData\Windows Update Agent (de362a425905bcc4)\`.
**Action:** on-prem partners should disable the listed extensions now and not reinstall them. Update servers, and every technician client to **26.6.5+**. Disabling extensions and patching do **not** remove existing persistence, so hunt for the service and path above and for unknown ScreenConnect clients.
**Sources:** [The Hacker News](https://thehackernews.com/2026/11/connectwise-warns-screenconnect-attacks.html), [SecurityWeek](https://www.securityweek.com/msp-screenconnect-servers-targeted-in-month-long-campaign/), [Huntress](https://www.huntress.com/blog)
